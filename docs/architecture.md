# Numen Architecture Reference

This document captures architectural decisions, naming conventions, and the
reasoning behind them.  It supplements `DESIGN.md` (high-level vision) and
`CLAUDE.md` (how-to guide).

---

## Field types and their roles

Every field annotation on a `Component` declares exactly how that field enters
the numerical layer.  The annotation is the **sole source of truth** — the
compiler, backends, and Julia runner all derive behaviour from it.

| Annotation | Vector | Updated by | Backed |
|---|---|---|---|
| `IntegratedField(size=N)` | state `x` | ODE solver (`ẋ = f(...)`) | ✓ all backends |
| `ParameterField(size=N)` | param `p` | never (constant for the solve) | ✓ all backends |
| `ContinuousField(size=N)` | state `x` | dynamics fn writes each RHS call | ✓ output; `algebraic=True` → Julia-only DAE |
| `DiscreteField(dt, size=N)` | state `x` | controller callback at multiples of `dt` | ✓ tstops; Python callback via `Callback` |

### `size=N` — vector fields

Any field can hold a contiguous array of `N` scalars by passing `size=N`.
The compiler packs them as `N` consecutive slots in `x` (or `p`).
All backends support this today.

```python
class VibeComponent(Component):
    kind:        Literal["vibe"] = "vibe"
    frequencies: Annotated[list[float], ParameterField(size=8)] = [0.0] * 8
```

The value's length must match `size`.  In dynamics, `spec.view(...).frequencies`
returns a numpy/JAX slice of length `N`.  In Julia, use
`param_range(spec, id * ".frequencies")` for the `UnitRange{Int}`.

## The `differential_mask` convention

### Why M is always 0/1 in numen

DAE solvers expect a **mass matrix** M in the system `M ẋ = f(x, p, t)`.
In many physics formulations M holds physical values — mass, heat capacity,
fluid capacitance.  **Numen never puts physical values in M.**

Instead, every dynamics function divides out the scaling factor:

```python
# Fluid accumulator — R·T/V is the capacitance
da.pressure += (cv.R_specific * cv.temperature / cv.volume) * mdot   # NOT: da.pressure += mdot

# Thermal node — heat capacity C divided out
db.temperature += Q_net / node.heat_capacity                          # NOT: db.temperature += Q_net

# Mechanics — mass divided out
dm.velocity += force / body.mass                                       # NOT: dm.velocity += force
```

The result: M is always a **diagonal 0/1 matrix**.

- `1` — this slot has a time derivative (`IntegratedField`, `DiscreteField`)
- `0` — this slot is algebraic; the dynamics fn writes a **constraint residual**
  (`ContinuousField(algebraic=True)`)

This diagonal 0/1 structure is what numen calls the **`differential_mask`**.
It is serialized as a flat list of floats (0.0 / 1.0) in `CompiledSpec` and
passed to Julia's `ODEFunction(dynamics!, mass_matrix=Diagonal(mask))`.

### Why this is domain-neutral

"Mass matrix" is Julia's / ODE literature's term for M.  It applies equally to
mechanical, thermal, fluid, and electrical systems — the word "mass" is
incidental.  In numen, the mask is purely structural: *does this variable have
a time derivative or not?*  Physical capacitances live in `p`.

### `ContinuousField` — two modes

| `algebraic` flag | Meaning | Differential mask | Backends |
|---|---|---|---|
| `False` (default) | **Output variable** — dynamics fn writes a derived quantity each RHS call (force, power, flow rate) | 1 (integrated like a state, but holds a computed value) | all |
| `True` | **Algebraic constraint** — dynamics fn writes a residual `g(x) = 0`; solver enforces the manifold | 0 (no time derivative) | Julia only (Rodas5P / FBDF / IDA) |

For the algebraic case, an implicit solver is **required**.  Numen checks this:
if any `ContinuousField(algebraic=True)` is present and the Julia solver is
explicit (Tsit5, Dopri5, Vern7), it raises a clear error before starting.

## Controller callbacks

### Architecture

Python-tier controllers run **between** ODE solver segments.  They are not
called inside the integrator loop (that is Julia's `PeriodicCallback` /
`DiscreteCallback` domain).

```
scipy:  solve(t0→t1) → controller(t1) → solve(t1→t2) → controller(t2) → …
JAX:    ✗  NumenFeatureError("control_callbacks") — JIT cannot call Python
Julia:  PeriodicCallback fires inside the integrator at t0+dt, t0+2dt, …
```

### Scipy segment-solve

The scipy backend breaks the integration at each controller fire time and
restarts with the updated state.  Steps:

1. Build `tstop_callbacks: dict[float, list[CompiledCallback]]` — which
   callbacks fire at each tstop (generated by enumeration, never by runtime
   float comparison).
2. Merge tstops within 1 µs to avoid near-zero-length segments from
   nearly-commensurate rates.
3. Call `solve_ivp((t_cur, t_stop), x_cur)` for each consecutive pair.
   `solve_ivp` hits `t_stop` exactly by shrinking the final adaptive step —
   zero simulation-time jitter.
4. After each segment: run all callbacks that fire at `t_stop`, apply the
   returned `{field_key: value}` dict to `x_cur`.
5. Stitch all segments into one `SolveResult`.

### Julia `PeriodicCallback`

Julia receives the callback list in the JSON payload.  The runner resolves
`julia_fn` (a `"Module.fn!"` string) from the already-loaded module scope —
the same pattern as `dynamics_fn` resolution in `build_dynamics`.  No
`eval` of arbitrary code; only symbol lookup in known scope.

User-side Julia signature:
```julia
function my_controller!(integrator, spec, params)
    # integrator.u  — current state x (writable)
    # integrator.p  — parameters p (read-only)
    # integrator.t  — current time
    # params        — Dict{String,Float64} from the Callback's params field
    i_force = state_idx(spec, "actuator.force")
    err = integrator.u[state_idx(spec, "sensor.angle")] - params["setpoint"]
    integrator.u[i_force] = params["kp"] * err
end
```

### Non-commensurate rates

With controllers at rates r1, r2, … the tstop timeline is the **union** of all
their fire times.  No LCM chunking.  For N controllers over a T-second
simulation, the number of segments equals `T * (r1 + r2 + … - overlaps)`.
Overlapping tstops (within 1 µs) are merged; both callbacks fire at the
earlier time.

## Backend compatibility matrix

`compile_spec()` sets `required_features: frozenset[str]` on `CompiledSpec`.
Every `backend.solve()` checks `required_features ⊆ supported_features` before
starting and raises `NumenFeatureError` with an actionable message.

| Feature | Scipy | JAX | JuliaBackend | JuliaServerBackend |
|---|:---:|:---:|:---:|:---:|
| `vector_fields` (size > 1) | ✓ | ✓ | ✓ | ✓ |
| `discrete_fields` (DiscreteField) | ✓ | ✓ | ✓ | ✓ |
| `continuous_fields` (ContinuousField output) | ✓ | ✓ | ✓ | ✓ |
| `control_callbacks` (Callback in world) | ✓ | ✗ | ✓ | ✓ |
| `dae_constraints` (ContinuousField algebraic=True) | ✗ | ✗ | ✓ | ✓ |

Adding support in a backend: add the string to `supported_features` ClassVar.
Removing support: remove it — affected models fail early with a clear message.

## Logging

```python
from numen.logging import configure_logging
import logging
configure_logging(level=logging.DEBUG)   # all diagnostics + Julia output
configure_logging(level=logging.INFO)    # solve start/finish only
```

Logger hierarchy: `numen.backend.scipy`, `numen.backend.jax`,
`numen.backend.julia`, `numen.backend.julia_server`.  Julia stderr is
routed to the logger in real time (not only on failure).
