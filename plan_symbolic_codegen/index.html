    Plan: Symbolic Codegen + Julia-First Roadmap

    Strategic context

    The framework's two-language burden (write dynamics in Python and Julia) is the primary friction today. The fix is symbolic codegen: write dynamics once in SymPy, auto-generate the Julia function.

    A related strategic observation: given modern AI assistance (Claude Code, etc.), the marginal cost of knowing Julia syntax is low. The Python scipy / JAX backends exist for development convenience, but Julia outperforms them by 600–1500×. The plan below is written with a Julia-first trajectory in mind — scipy/JAX stay for debugging but are not the target path.

    What we're building

    A symbolic_rhs hook on System that:

    1. Lets the user express dynamics as SymPy expressions (same conceptual API as the existing python_fn but symbolic)
    2. Auto-generates a complete .jl file for the Julia backend
    3. Optionally auto-generates a Python callable (for scipy/JAX validation — secondary)

    Users who adopt this path write no Julia by hand. The generated file is human- readable and can be committed to the repo (stable output for the same world).

    API design

    The symbolic_rhs classmethod

    class SpringForceSystem(System):
    component_types: ClassVar[tuple[type, ...]] = ()
    entity_slots:    ClassVar[EntityGroup]      = EntityGroup(MassComponent, SpringComponent, MassComponent)
    kind:            Literal["spring_force"]    = "spring_force"
    dynamics_fn:     str = "Generated.spring_force!"   # auto-set by codegen

    @classmethod
    def symbolic_rhs(cls, sym: "SymbolicSpec") -> None:
        a  = sym.view("a", MassComponent)      # role "a" = first slot in entity_slots
        s  = sym.view("s", SpringComponent)
        b  = sym.view("b", MassComponent)
        da = sym.dx_view("a", MassComponent)
        db = sym.dx_view("b", MassComponent)

        force = s.k * ((b.position - a.position) - s.rest_length)
        da.velocity += force / a.mass
        db.velocity += -force / b.mass

    The SymbolicSpec mirrors the existing CompiledSpec API exactly — view() and dx_view() return objects whose attributes are SymPy symbols instead of array slices. This means the symbolic fn looks nearly identical to the existing Python fn.

    Single-entity shorthand

    For systems with component_types (auto-populated entity_groups), the single-slot role is called "e" by convention:

    @classmethod
def symbolic_rhs(cls, sym: "SymbolicSpec") -> None:
    ball = sym.view("e", BallComponent)
    db   = sym.dx_view("e", BallComponent)
    db.position += ball.velocity
    db.velocity += -9.81

    Generated Julia output

    For the spring system above, generate_julia(world, "dynamics.jl") produces:

    # Auto-generated by numen.codegen — do not edit by hand.
# Source: SpringForceSystem.symbolic_rhs
module Generated

import Main: CompiledSpec, CompiledSystemSpec, state_idx, param_idx

function spring_force!(
    dx::Vector{Float64}, x::Vector{Float64}, p::Vector{Float64},
    t::Float64, spec::CompiledSpec, sys::CompiledSystemSpec,
)
    gs = sys.group_size
    for i in 1:gs:length(sys.entity_ids)
        id_a = sys.entity_ids[i]
        id_s = sys.entity_ids[i + 1]
        id_b = sys.entity_ids[i + 2]

        position_a  = x[state_idx(spec, id_a * ".position")]
        velocity_a  = x[state_idx(spec, id_a * ".velocity")]
        mass_a      = p[param_idx(spec, id_a * ".mass")]
        k           = p[param_idx(spec, id_s * ".k")]
        rest_length = p[param_idx(spec, id_s * ".rest_length")]
        position_b  = x[state_idx(spec, id_b * ".position")]
        velocity_b  = x[state_idx(spec, id_b * ".velocity")]
        mass_b      = p[param_idx(spec, id_b * ".mass")]

        dx[state_idx(spec, id_a * ".velocity")] += k * (position_b - position_a - rest_length) / mass_a
        dx[state_idx(spec, id_b * ".velocity")] += -(k * (position_b - position_a - rest_length)) / mass_b
    end
end

end  # module Generated

    sympy.julia_code(expr) handles the expression body. The codegen wrapper handles: - Variable reads (x / p lookups per role+field) - The entity loop with correct stride - dx[...] += write pattern - Module header and function signature

    Implementation plan

    Phase 1 — MVP (scalar fields, single output file)

    New files: - src/numen/codegen/symbolic.py — SymbolicSpec, SymbolicComponentView, SymbolicDerivativeView - src/numen/codegen/julia_gen.py — generate_julia(world, output_path)

    Changes to existing files: - src/numen/spec/system.py — add symbolic_rhs: ClassVar[Callable | None] = None - src/numen/compiler/flatten.py — compile_spec() sets dynamics_fn on systems that have symbolic_rhs but no explicit dynamics_fn

    SymbolicSpec internals:

    @dataclass
class SymbolicSpec:
    entity_slots: EntityGroup      # slot order defines role→index mapping

    # After symbolic_rhs(sym) call:
    _reads:  dict[str, sympy.Expr]   # {role.field: symbol}
    _writes: dict[str, sympy.Expr]   # {role.field: expression}

    view("a", MassComponent) creates and caches SymPy symbols named position_a, velocity_a, mass_a etc. dx_view("a", MassComponent) returns a view that accumulates += into _writes["a.velocity"].

    generate_julia(world, output_path) steps: 1. Walk world.systems; skip any with no symbolic_rhs 2. For each system: call symbolic_rhs(SymbolicSpec(system.entity_slots)), collect _reads and _writes 3. Emit Julia module header 4. For each system: emit the function using the template above 5. Write to output_path; also set system.dynamics_fn = "Generated.<fn_name>!" on any system that was missing it

    Scope of Phase 1: - Scalar IntegratedField and ParameterField only - No algebraic (DAE) slots - Single output module Generated containing all system functions - No Python lambdify

    Deliverable: generate_julia(make_world(), "dynamics.jl") works for the oscillator and coupled_spring examples end-to-end.

    Phase 2 — Vector fields + algebraic slots

    • size=N fields: SymbolicComponentView returns a sympy.Matrix for vector fields; julia_gen.py emits the corresponding range reads/writes
    • ContinuousField(algebraic=True): residual form — dx_view().field += residual_expr generates dx[state_idx(...)] += <expr> (unchanged structurally, but DAE-flagged for the mass-matrix path)

    Phase 3 — Python auto-fn (optional, for validation)

    Auto-generate a python_fn via sympy.lambdify that is JAX-compatible (modules=["jax.numpy", "numpy"]). This is lower priority given the Julia-first direction, but useful for: - Smoke-testing dynamics before the Julia solve - Keeping scipy/JAX backends working without hand-written Python dynamics

    Phase 4 — CLI integration

    uv run numen generate dynamics.jl   # generate for current directory's world.py
uv run numen check --generate       # generate then run check

    numen generate reads world.py::make_world() via importlib, calls generate_julia(world, "dynamics.jl"), prints a summary of generated functions.

    Scope boundaries

    In scope: - Pure algebraic expressions (polynomials, trig, sqrt, exp, log) - Any expression sympy.julia_code() can handle - Scalar and vector state/param fields - Single-module output

    Out of scope / escape hatch: - Lookup tables, interpolation, external data → user still writes Julia by hand - Piecewise / Piecewise expressions → use Julia's ifelse() / jnp.where() pattern; sympy.julia_code handles Piecewise but with branching (fine for Julia, not JAX) - The generated file is a starting point — users are free to extend it manually

    Julia-first roadmap (broader picture)

    Given that Julia solves 600–1500× faster and AI assistance removes the language barrier, the longer-term simplification is:

    Now After symbolic codegen
    Write python_fn (scipy/JAX) + dynamics_fn string (Julia) Write symbolic_rhs once
    python_fn: ClassVar required on System Optional; auto-generated or omitted
    Two files to keep in sync One source of truth

    scipy / JAX backend status: - Keep as "development/validation" backends, not the primary path - python_fn remains supported but no longer required when symbolic_rhs is present - Long-term: scipy/JAX may be marked legacy once symbolic → Python codegen works

    What Python continues to own (permanently): - Spec authoring (Pydantic components, systems, world) - compile_spec() and JSON serialization - SnapshotCollector + post-processing - JuliaServerPool for parameter sweeps - generate_julia() codegen

    This is the cleanest possible split: Python = spec + data + analysis; Julia = math.

    Open questions before Phase 1

    1. Module naming — single Generated module or one module per system class? Single module is simpler; separate modules allow partial regeneration.

    2. Determinism — should generate_julia() be idempotent (always overwrite) or refuse to overwrite hand-edited files? Suggest: always overwrite, but warn if the file contains a # hand-edited sentinel comment.

    3. dynamics_fn auto-assignment — mutating world.systems after construction conflicts with Pydantic's frozen models. Options: (a) return a modified world copy, (b) let generate_julia() only write the file and require the user to set dynamics_fn manually in world.py, (c) make dynamics_fn optional and have the Julia backend derive it from the module name convention. Option (b) is simplest for Phase 1.

    4. SymPy as a hard dependency — currently optional. Add to pyproject.toml as an optional [codegen] extra or make it required? Suggest: required (it's small and the framework's value prop depends on it).
